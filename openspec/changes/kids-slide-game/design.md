## Context

這是一個全新的網頁休閒遊戲專案，目前沒有任何既有程式碼或框架限制。目標是快速做出一個可在瀏覽器執行、僅需滑鼠操作、單機無後端的無限模式（Endless）小遊戲：小朋友沿垂直軌道持續下滑，玩家拖曳滑梯零件填補前方空格，一旦小朋友滑到空格即遊戲結束。核心挑戰在於：軌道的程序化生成與捲動、零件佇列的供給、以及滑鼠拖放到 Canvas 座標系統的互動判定。

## Goals / Non-Goals

**Goals:**
- 建立可執行、可玩的網頁版無限模式原型：軌道生成、零件拖放、失敗判定、分數與最高分。
- 操作僅需滑鼠（拖曳），不考慮觸控與手把輸入。
- 遊戲邏輯與渲染邏輯分離，方便後續調整難度曲線與視覺風格。
- 純前端、無後端依賴，最高分使用瀏覽器 localStorage 儲存。

**Non-Goals:**
- 不做多人連線、排行榜伺服器、帳號系統。
- 不做觸控/行動裝置最佳化（先以桌面瀏覽器為主）。
- 不做關卡制內容（本次僅無限模式）。
- 不處理美術資源產線（先用簡單幾何圖形/佔位美術）。

## Decisions

### 1. 渲染方式：HTML5 Canvas 2D
使用 Canvas 2D API 繪製軌道、小朋友、零件佇列與 UI 疊層，搭配 `requestAnimationFrame` 驅動遊戲迴圈。
- 替代方案考慮：
  - DOM + CSS transform：對少量元素尚可，但軌道區塊數量隨捲動持續變動，DOM 節點增刪成本較高。
  - WebGL：效能過剩，對這種簡單 2D 圖形不必要地增加複雜度。
- 選擇 Canvas 2D 是效能與開發複雜度的平衡點。

### 2. 語言與建置工具：TypeScript + Vite
使用 TypeScript 撰寫遊戲邏輯以取得型別安全（尤其是軌道資料結構與方向判定），Vite 作為開發伺服器與打包工具，最終輸出純靜態網頁（HTML/JS/CSS），可直接部署到任何靜態主機。

### 3. 軌道資料模型：以「列（row）」為單位的區塊佇列
軌道視為由下往上（或由上往下）依序排列的區塊（segment），每個區塊有：
- `type`: `straight` | `curve-left` | `curve-right` | `empty`（空格，尚未鋪設）
- `entryDirection` / `exitDirection`: 決定與前後區塊是否能合法銜接
- 軌道採「捲動視窗」設計：只在記憶體中保留小朋友前後可視範圍內的區塊，超出畫面上方（已通過）的區塊移除，並持續在下方生成新區塊（含隨機出現的 `empty` 空格）。

### 4. 零件佇列與供給機制
維護一個固定長度（例如 5 個）的「待放置零件佇列」，顯示於畫面側邊或下方。佇列內容隨機產生（`straight` / `curve-left` / `curve-right`），玩家每放置一個零件，佇列補入一個新的隨機零件，確保玩家永遠有零件可用。

### 5. 拖放互動：自訂 Pointer Event 拖曳（非原生 HTML5 Drag and Drop API）
在 Canvas 上以 `pointerdown` / `pointermove` / `pointerup` 自行實作拖曳邏輯：
- `pointerdown` 於佇列中的零件上時，開始拖曳，該零件跟隨滑鼠移動並繪製於最上層。
- `pointerup` 時偵測滑鼠座標是否落在某個合法的空格區塊範圍內。
- 若落在合法空格：檢查該空格是否能與前一段軌道的 `exitDirection` 銜接（方向匹配），合法則放置成功、移除佇列該零件並補充新零件；不合法則零件回彈到佇列原位並給予輕微視覺回饋（例如短暫紅色閃爍）。
- 若沒有落在任何空格範圍：零件回彈到佇列原位。
- 選擇自訂實作而非原生 HTML5 Drag and Drop API，因為原生 API 是針對 DOM 元素設計，與 Canvas 座標系統整合成本較高，且原生 API 在拖曳視覺回饋（跟隨游標、非原生外觀）上限制較多。

### 6. 遊戲迴圈與難度曲線
使用固定時間步（fixed timestep）更新遊戲狀態，小朋友的下滑速度為距離的遞增函數（例如 `speed = baseSpeed + k * distanceTraveled`，上限封頂避免後期操作不可行）。速度上升會同時加快軌道生成/捲動速度與空格出現頻率（在合理範圍內），提高後期挑戰性。

### 7. 失敗判定
每個更新影格檢查小朋友目前所在的區塊：若小朋友的位置到達某個區塊的判定線，且該區塊仍是 `empty`（尚未被放置合法零件），立即觸發「掉落」，遊戲進入 Game Over 狀態並停止更新。不設生命值/緩衝機制（依先前確認：一次落空即結束）。

### 8. 狀態管理與資料持久化
簡單狀態機：`menu` → `playing` → `gameOver`（可重新開始回到 `playing`）。分數以「存活距離」計算，遊戲結束時比對並更新 `localStorage` 中的最高分並顯示於結果畫面。

## Risks / Trade-offs

- [風險] 自訂 Pointer 拖曳在放置判定的容錯範圍（空格點擊區域大小）設計不當，可能導致操作手感差 → 緩解：空格判定範圍略大於視覺區塊本身，並在放置成功/失敗時提供即時視覺與（可選）音效回饋。
- [風險] 難度曲線（速度遞增函數）若調校不當，可能造成後期速度暴衝導致無法遊玩 → 緩解：速度成長設定上限（cap），並在原型階段以實際遊玩測試微調參數。
- [風險] 軌道空格與零件方向的隨機生成若沒有做「可解性」保證，可能出現無論如何都無法合法銜接的情況（例如彎道方向與前段出口方向永遠不匹配）→ 緩解：空格生成時，需求的零件方向集合必須至少包含佇列中已存在或即將產生的可用零件類型，或簡化規則讓多數零件類型皆可銜接大部分空格。
- [取捨] 選擇 Canvas 2D 而非 DOM，換取效能與捲動彈性，但犧牲了部分 CSS 動畫/樣式的便利性，UI 疊層（分數、Game Over 畫面）仍可用 DOM 覆蓋在 Canvas 上方處理。

## Migration Plan

全新專案，無既有系統需要遷移或相容處理：
1. 以 Vite 建立 TypeScript 專案骨架。
2. 實作核心遊戲迴圈與軌道渲染（先不含拖放，驗證捲動與速度曲線）。
3. 加入零件佇列與拖放放置邏輯。
4. 加入失敗判定與 Game Over／重新開始流程。
5. 加入分數與 localStorage 最高分記錄。
6. 視覺與回饋微調（放置成功/失敗提示、UI 排版）。
無需 rollback 策略（尚無上線版本），若需求變更可直接調整對應模組。

## Open Questions

- 空格與零件方向的「可解性」規則細節（例如是否允許彎道連續同方向、是否限制空格最大連續數量）需要在實作 `slide-track` 時進一步定義具體演算法參數。
- 是否需要基本音效/音樂（本次 proposal 未明確要求，先視為可選、非必要項目）。
- 視覺美術風格（色票、角色造型）留待後續美術階段決定，不影響本次核心玩法規格。
